# Plan: a reranker behind the FilingReranker boundary (Follow_Ups RAG-1)

Orchestrated build per CLAUDE.md. Three serial milestones with contracts written before code. Branch: `reranker`
from `main`. Build: `set -a; source .env; set +a; ./mvnw -q verify`; never export the application enable flags
or `RAG_*` overrides in a shell that runs tests.

## Why

Snapshot 91 (set v2, current defaults) misses msft-08, nvda-02, nvda-04, nvda-07, nvda-09 outright, and NVDA is
the weakest ticker at hit@5 0.643. For nvda-02, nvda-07, and nvda-09 retrieval already returns the right
filing and section but a neighbouring chunk ranks above the answer. Fusion orders chunks by list positions; it
never reads a chunk against the question. A reranker does: it scores each (question, chunk) pair directly and
reorders the top of the fused list. The `FilingReranker` interface, the `rag.retrieval.reranking-enabled` switch,
the `HYBRID_RRF_RERANKED` strategy, and `validateRerankedEvidence` (a reranker may only reorder and subset the
candidates it was given) already exist; no implementation does.

## Decision (Jay, 2026-09-13): Option A, local cross-encoder

Chosen in chat on 2026-09-13, which also approved the two Maven dependencies and the one-time model download named
below. Options B (OpenAI small chat model as a listwise reranker, about 3,000 to 7,000 extra tokens per
recommendation run and 140,000 per evaluation run, promptable) and C (defer) were declined.

- **Option A, local cross-encoder.** `cross-encoder/ms-marco-MiniLM-L-6-v2` run on the CPU through
  ONNX Runtime for Java, with its Hugging Face tokenizer. No model tokens, no provider rate limit, deterministic,
  and it reads each chunk as data with no instruction channel, so it cannot be prompt-injected. Costs: two new
  Maven dependencies with native libraries (`com.microsoft.onnxruntime:onnxruntime`,
  `ai.djl.huggingface:tokenizers`), and a one-time download of `onnx/model.onnx` (about 90 MB) and
  `tokenizer.json` (under 1 MB) from huggingface.co/cross-encoder/ms-marco-MiniLM-L-6-v2, stored outside git
  (path configured, checksum recorded). General-domain training (web search), so financial fit must be measured.
  Expected latency on 20 pairs: a few hundred milliseconds.

## Design constraints

- Reranking is applied to the first `rag.retrieval.rerank-candidates` (default 20, range 5..40) of the fused,
  diversified list; the rest are dropped, since topK is at most 20. `similarityScore` keeps meaning cosine
  similarity; the reranker's own score is not written into it.
- Any reranker failure or timeout (`rag.retrieval.rerank-timeout-ms`, default 2000) falls back to the fused order
  with strategy `HYBRID_RRF` and a WARN naming the exception class only; retrieval never fails because of it.
- Off by default until Milestone 3 measures it. `RetrievalRequest.rerank` and `POST /api/rag/evaluate?rerank=`
  override the property per call, like `hybrid`. Snapshot `properties` record whether reranking ran and the
  reranker's name and version.

## Milestone 1: per-call override and evaluation plumbing, no model

Scope: `rerankCandidates` and `rerankTimeoutMs` properties; `RetrievalRequest.rerank` (null = property);
`?rerank=` on evaluate, recorded in snapshot properties with the reranker name (null when none); timeout and
fallback around the existing reranker call; a test-only reranker that reverses the candidate order to prove the
path end to end.

Correctness contract:
- C1. With a scripted reranker, `rerank` true reorders the first `rerankCandidates` fused candidates and returns
  topK of them with strategy `HYBRID_RRF_RERANKED` (or `FILTERED_VECTOR_RERANKED` with hybrid off); false leaves
  the fused order; null follows the property; true with no reranker bean fails the request with a clear 400-class
  error rather than silently skipping.
- C2. A reranker that throws, or exceeds the timeout, yields the fused order with the non-reranked strategy and a
  WARN without the exception message; the evidence validator still rejects a reranker that returns a chunk it was
  not given or more than topK.
- C3. `similarityScore` of every returned chunk equals its fused-list value.
- C4. Evaluation records `rerank` and `reranker` in properties; existing snapshots read back unchanged.
- Commands: `./mvnw -q -o verify` exit 0.
- Out of scope: any real reranker, dependencies, downloads, measurement.
- User-facing flow: none (Scrutiny only).

## Milestone 2: the cross-encoder reranker

Correctness contract:
- C1. `CrossEncoderReranker` loads the model and tokenizer from `rag.retrieval.cross-encoder.model-path` and
  `tokenizer-path` at startup only when reranking can run; a missing file or checksum mismatch fails startup with a
  message naming the path, and the application still starts normally when reranking is disabled.
- C2. Scores each (question, chunk) pair with the chunk cut to the model's 512-token window; orders by score, ties
  by fused order; returns topK; deterministic across two calls on the same input (identical order and scores).
- C3. A DB-free integration test runs the real model on three handwritten pairs where one chunk answers the
  question and two do not, and the answering chunk ranks first; the test is opt-in (`-Drag.rerank.live=true`)
  because the model file is not in git.
- C4. Latency for 20 candidates logged; the timeout path exercised with an artificially small timeout.
- C5. The download is recorded in `documentation/live-runs/` with URL, file sizes, and SHA-256, and the files
  sit under a gitignored directory.


## Milestone 3: measure, decide, document

Scope: on set v2, run evaluation with rerank off (reference snapshot 91 conditions) and on at `rerank-candidates`
10, 20, and 40. Selection rule: enable by default only if aggregate hit@5 does not decrease, non-figure hit@5
does not decrease, no ticker's hit@5 decreases, and no FIGURE question in the top 5 under the reference leaves it;
among qualifying rows prefer the highest MRR, then fewer candidates. Both floors re-derived only upward. RAG.md,
Follow_Ups RAG-1, PRD phase 3, evidence directory, latency or token cost per run stated.

Correctness contract: tables match stored snapshots by id; defaults equal the rule's choice with the rule shown
row by row; both floors pass with the final defaults; the per-slice decomposition is reported so an improvement on
figure questions cannot hide a loss on ordinary ones.

User-facing flow (UT Validator): nvda-02's question retrieved with `rerank` true and false; ranks match the
documented table; strategy labels correct.

## Gate rules

Both validators must pass before the next milestone; at most two remediation rounds, then escalate. Validators
never see the Worker's report or each other's output. Scrutiny recomputes metrics from stored ranks and checks
failure messages name what they guard.

## Amendment 1 (2026-09-13, after Milestone 1 Scrutiny PASS)

Milestone 1 passed. Its non-blocking notes change Milestone 2's contract because Milestone 3's measurement depends
on them:

- **Record whether reranking actually ran, per question.** Snapshot `properties.rerank` is the requested override,
  and `retrievalStrategy` is taken from the first question only, so a cold-start timeout on one question mislabels
  the whole run, and fallbacks on later questions are invisible. Milestone 2 adds: each question result records its
  `retrievalStrategy`; the snapshot records `rerankedQuestions` and `rerankFallbackQuestions` counts; a run with any
  fallback is visible in the API response and in the live-test output.
- **No silent truncation below topK.** With `rerank-candidates` below the requested topK, a reranked response would
  hold fewer chunks than requested. The reranker input becomes the first max(`rerank-candidates`, topK) candidates,
  documented in `application.yaml` and RAG.md. The Milestone 3 grid (10, 20, 40 at window 10) is unaffected.
- **`Error` from a reranker.** Such an `Error` still propagates; the service Javadoc and RAG.md say so instead of
  claiming retrieval "never fails" because of the reranker. The reranker name uses the user class (no proxy suffix).
- **Bean creation versus default use.** `rag.retrieval.cross-encoder.enabled` (default false) creates the reranker
  bean and checks its files at startup; `rag.retrieval.reranking-enabled` stays the default for whether retrieval
  uses it. With the cross-encoder disabled, `rerank: true` keeps Milestone 1's 400.
- **Snapshot version.** `properties` add `rerankerVersion`: the first 12 hex characters of the model file's
  SHA-256, so a snapshot names the exact model it used.
- **Milestone 2 user-facing flow (UT Validator).** App started with the cross-encoder enabled and reranking off by
  default: `POST /api/rag/retrieve` for nvda-02's question with `"rerank": true` returns `HYBRID_RRF_RERANKED` and
  the same chunk order on two consecutive calls; without `rerank` it returns `HYBRID_RRF`; app restarted with the
  cross-encoder disabled, the same request with `"rerank": true` returns 400. No evaluation run.
- **Download boundary.** Approved: Maven dependencies from Maven Central and the two files from
  huggingface.co/cross-encoder/ms-marco-MiniLM-L-6-v2. If any dependency tries to download native libraries or
  other files at runtime from anywhere else, the Worker stops and reports rather than allowing it.

## Amendment 2 (2026-09-13, before Milestone 3)

Milestone 2 passed after two remediation rounds and, at the cap, a documentation correction Jay chose to have the
Orchestrator apply directly, confirmed by a docs-only Scrutiny check. Milestone 3 changes:

- **No automatic default flip.** Enabling reranking by default needs `rag.retrieval.cross-encoder.enabled: true`, and
  Milestone 2 made startup fail when the model files are missing. The files are gitignored by design, so a default flip
  would break startup on any machine or clone without them. If the selection rule qualifies a configuration, the Worker
  records the recommendation and the exact properties to set, leaves both defaults false, and the decision goes to Jay.
- **Files the Worker must not touch.** The working tree holds someone else's uncommitted edits to
  `src/main/java/PRD_Stock_Recommendation_Engine_v3.md` and `src/main/java/documentation/Follow_Ups.md`, and an untracked
  `src/main/java/documentation/Target_State_Trading_Desk.md`. The Worker neither edits, stages, nor reverts them; the
  Follow_Ups RAG-1 row and the PRD phase row are updated by the Orchestrator with Jay afterwards.
- **Only runs without fallbacks count.** A run with `rerankFallbackQuestions` above zero did not measure the reranker on
  every question. The first call after startup was measured at about 4 s end to end, above the 2,000 ms rerank timeout,
  so the Worker warms the reranker with one retrieval after each start and before the evaluation. A run that still
  reports fallbacks is rerun once; if fallbacks persist, it is reported as invalid and excluded from the rule.
- **Latency reported per run**, from the reranker's log lines: median and maximum scoring time per question.
